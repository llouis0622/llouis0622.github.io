한 달 동안 파서로 뽑아낸 객체가 237개였다. 정확하긴 한데, 이걸 그대로 그래프로 보여주면 아무도 못 읽는다. 그래서 설계를 뒤집었다. **기본 업무 개념 17개 + 펼쳐 보는 상세 기록.** 기존 237개 객체는 원천 근거로 보존하고, 사용자가 보는 지도는 실제 업무 명사로 다시 구성한다.

<!--more-->

## 17개 업무 개념

```text
생산        ① 작업지시  ② 생산작업  ③ 공정정의  ④ 설비
기준 정보   ⑤ 사업장  ⑥ 거래상대  ⑦ 품목정의  ⑧ 제품규격
재고·실물   ⑨ 자재/제품로트  ⑩ 창고  ⑪ 재고잔량  ⑫ 재고수불
구매·영업   ⑬ 구매입고  ⑭ 수주  ⑮ 출하계획  ⑯ 출고  ⑰ 매출 기록
```

품목 · 규격 · 로트 · 재고는 합치지 않는다. "어떤 제품인지", "어떤 치수인지", "어느 실물인지", "얼마나 남았는지"는 서로 다른 질문이기 때문이다. 거래상대도 하나의 회사가 여러 역할을 맡을 수 있게 하되, 판매처 · 수요가 · 매입처라는 역할은 유지한다.

질문 중심 설계, 별칭 활용, 수정 이유 · 이력 관리 같은 원칙은 공개된 KB 온톨로지 글 시리즈와 Palantir의 업무 객체 설계 가이드에서 가져왔고, 우리 DB의 실제 키와 MES 연결 근거에 맞춰 조정했다.

## 계획과 실행을 분리한다

작업지시(계획)와 생산작업(실행)은 다른 노드다. 지시 1건에 작업 여러 건이 연결될 수 있고, 계획투입 · 실제투입 · 산출은 각각 별도 기록과 키를 유지한다. 영업 쪽도 수주 → 출하계획 → 출고 → 매출을 문서로 구분하고, 거래 역할은 관계로 표현한다.

중요한 건 **강제로 잇지 않는 것**이다. 이 회사는 재고 생산이 중심이라 "고객 → 수주 → 생산 → 출고"를 모든 건에 강제하면 틀린다. 실제로 연결되는 배정 · 추적 근거가 발견되면 그때 연결한다.

## 무엇을 노드로, 무엇을 속성으로

독립적으로 선택하거나 이력을 추적할 대상은 노드, 그것을 설명하는 수량 · 중량 · 날짜 · 상태 · 금액은 속성이다. 진행률 · 남은 생산량 · 확정 매출액 같은 지표는 노드가 아니라 **계산 정의**로 관리한다. 이렇게 해야 "수량", "코드", "일자" 같은 점이 수백 개 생겨 화면을 덮는 일을 막는다.

## 하나의 연결에도 세 개의 키

```text
실적산출 상세 → 생산지시 상세
  법인코드 + 지시번호 + 지시상세번호  세 키를 함께 써야 원 지시를 찾는다
  지시번호만 같다고 연결하면 다른 상세가 섞인다
  연결된 실적이 여러 행이라고 계획량을 여러 번 더하면 안 된다
```

"같은 뜻으로 검색하기", "같은 업무 개념으로 묶기", "같은 실제 대상을 합치기", "두 테이블을 조인하기"는 각각 별도 판단이다. 용어 하나를 승인했다고 나머지까지 자동 승인되면 안 된다.

## 사람은 이 화면만 보면 된다

```text
검토 대상: 실적산출 → 생산지시 상세
제안한 뜻 / 원천 테이블 / 연결키 / 근거 / 주의 / 행 검증 상태
[뜻·이름 승인] [다른 뜻으로 분리] [수정 요청] [보류]
```

엔진은 근거와 충돌을 묶어 제시하고, 사람은 "업무상 맞는 뜻인가", "다른 역할을 합치지 않았나", "계산 기준이 맞나"만 판단한다. 변경 이유와 이전 정의는 남긴다.

## CSV 검증이 알려준 것

실제 추출본을 검증하자 설계를 한 번 더 고쳐야 했다. **'자재가 기록된 작업'과 '그 자재를 실제 사용한 작업'이 다르다.** 다른 작업의 자재 기록을 참조하는 사용 내역이 34,660행 확인됐다. 그래서 자재투입기록 ↔ 작업별 스켈프 사용기록 ↔ 산출기록을 분리했고, 대응이 하나로 확인된 범위만 연결하며 여러 후보가 나오면 임의 선택하지 않는다.

산출량은 산출기록에서, 사용량은 사용기록에서 읽는다. 사용기록에 반복된 생산수량까지 더하면 산출량이 부풀어진다.

예외도 보존한다. 부모 없는 계획투입, 산출 없는 작업, 계획 없는 출고, 마스터에 없는 과거 품목, 날짜가 역전된 자재 참조. 삭제하거나 자동 보정하지 않고 **이유와 함께 표시**한다.

## 제작 순서

1. 전체 기간 데이터 반입 (생산 7개 표 약 30만 행 + 기준정보, 개인정보 제외, 원본 보존)
2. 대량 자료 조회 기반 (검증 후 버전별 적재, 반입 실패 시 기존 자료 유지)
3. 실제 건을 선택하고 질문 (답변에 사용한 관계만 그래프에서 강조)
4. 원본과 대조 (행수 · 전체 키 · 중복 · 누락 · 참조 · 정밀도)

단위나 계산 규칙이 불명확한 지표는 추측하지 않는다. 먼저 기록에 적힌 값을 정확히 조회하는 것부터 완성한다.
