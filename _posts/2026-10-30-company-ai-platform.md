회사 AI 서버에 Orca를 올리고 Claude Code · Codex로 여러 프로젝트를 운영하게 되면서, **AI 사용 현황을 확인하고 프로젝트 경험을 전사 공통 자산으로 발전시키는 구조**를 설계하는 일을 맡았다. 설계 문서와 의사결정 문서 두 가지를 썼다. (서버 · 계정 정보는 제외했다.)

<!--more-->

## 추천 구성

PostgreSQL을 업무 · 운영 데이터의 중심 DB로 두고, **공통 문서 · 스킬 · 룰 · 훅의 원본은 Git 저장소에서 관리**한다.

| 구성 요소 | 역할 |
|---|---|
| PostgreSQL | 사용자 · 프로젝트 · AI 세션 · 사용량 · 지식의 상태와 관계 |
| 공통 자산 Git 저장소 | 문서 · 스킬 · 룰 · 훅의 변경 이력과 버전 |
| 프로젝트별 Git 저장소 | 코드와 프로젝트별 문서 · 설정 · 인수인계 |
| Orca · Claude Code · Codex | 프로젝트 작업과 공통 지침 활용 |
| 사내 AI 대시보드 | 사용 현황, 공통 자산, 지식 검색, 승인 · 배포 현황 |
| pgvector (필요 시) | 의미 기반 오류 · 문서 검색 |

MariaDB도 가능한 대안이다. 11.7부터 벡터 검색을 지원하므로 "벡터 검색이 되니까 PostgreSQL"은 이유가 못 된다. 회사의 운영 경험이 어디에 있는지가 더 중요하다.

## 지식이 쌓이고 되돌아오는 흐름

```text
프로젝트 작업 → 오류·개선 방법 후보 등록 → 담당자 검토·승인
  → 공통 자산 Git 저장소 → 프로젝트별 지침·스킬 적용
  → (PostgreSQL) 검색·그래프·관리 화면 → 수정 제안 → 다시 후보로
```

프로젝트명 · 고객 정보 · 코드 · 계정이 포함된 원본을 전사에 자동 노출하지 않는다. 전사에 공유할 수 있는 요약과 원본의 접근 권한은 구분한다. 자동 생성된 지식은 승인 전까지 **후보**로 표시한다.

## Claude Code와 Codex에 적용하기

Claude Code는 `CLAUDE.md` · 스킬 · 훅, Codex는 `AGENTS.md` · 스킬. 하나의 회사 기준을 각 도구가 읽을 수 있는 형태로 연결하거나 배포한다. 다만 **서버에 파일을 올렸다고 모든 세션에 자동 적용된다고 가정하지 않는다.** 각 도구에서 실제로 어떤 지침이 로드되는지 시험한다.

지침 문서만으로 AI의 행동이 강제되지는 않는다. 사람이 승인하지 않은 병합 금지 같은 통제는 저장소 권한 · 브랜치 설정 · 검증 절차에서도 구현한다. 훅은 명령을 실행하므로 회사에서 검토 · 시험한 버전만 배포한다.

## 그래프와 온톨로지는 작게 시작

처음에는 "프로젝트에서 발생한 오류 → 해결 방법 → 문서 → 관련 스킬 → 적용 프로젝트" 정도의 관계만 일관되게 기록한다. PostgreSQL 테이블로 관계를 저장하고 화면에 표시하는 것부터 시작하고, 깊은 탐색이 실제로 필요해지면 그래프 DB를 검토한다. 접근 권한은 문서 본문뿐 아니라 검색 결과와 그래프의 노드 · 연결에도 적용한다.

## 기술보다 결정이 먼저였다

설계 문서보다 더 오래 걸린 건 **의사결정 문서**였다. 도입 범위 · 관리 웹 기능 · 접근 권한 · 계정과 로그인 · 네트워크 · AI 계정과 에이전트 실행 · 대화 보관 · GitLab/GitHub 운영 · 이슈 관리 · 배포 승인 · 백업 · 디자인팀 연계까지 13개 영역, 100개가 넘는 질문을 선택지 · 장단점 · 기존 초안과 함께 정리했다.

몇 가지만 꼽으면 이런 것들이다.

- AI 에이전트가 사람 승인 없이 어디까지 작업할 수 있나? (코드 수정 · 테스트는 자동, 병합 · 운영 배포 · 권한 변경은 승인)
- 대화 원문을 얼마나 보관하고 누가 볼 수 있나? 운영 DB 90일과 백업 90일을 합치면 약 180일까지 남을 수 있다는 점을 함께 알려야 했다.
- 공용 AI 계정으로 작업할 때 실제 사용자와 프로젝트를 어떻게 식별하나?
- GitLab 기준으로 작업하고 GitHub로 자동 반영할 때, GitHub에서만 만든 변경은 사라져도 되는가?

확인하지 못하는 값은 추정하지 않고 **미확인**으로 표시했다. 이 문서의 구조와 운영 방식은 제안이고, 권한 · 공개 범위 · 도구 선택은 회사가 결정한다. 엔지니어가 할 일은 선택지를 정확하게 만드는 것까지였다.
